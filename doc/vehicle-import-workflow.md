# Vehicle imports from an approved Blender master

Keep the Blender master untouched. Export through a background Blender process;
put export scripts, runtime adjustments, textures, wrappers and verification in
the game project. Inspect the closest existing vehicle before implementing one.

## Repeatable sequence

1. Read `AGENTS.md`, the asset checkpoint, the comparable model scene, vehicle
   catalog, factory, driving controller and test runner. Do not reopen an editor
   if the user's existing Godot editor is already connected through MCP.
2. Inspect source mesh/material counts, triangle count, world bounds, units,
   transforms, active material UV map, packed images and material node links.
   Merge meshes and consolidate materials before import if necessary. Preserve
   approved smooth/custom normals and keep special adjustable materials separate.
3. Export selected geometry only as glTF with separate textures and binary data.
   Disable cameras, lights and animation for a static merged vehicle. Keep only
   the UV set used by the atlas in the export copy. Use metres, Y-up and Godot
   forward -Z. Measure the couplers instead of inferring length from the cab/body.
   Center their envelope longitudinally for the game's half-length spacing.
   Do not raise the entire mesh to its lowest vertex: wheel flanges intentionally
   extend below the tread plane, which should remain at local Y=0.
4. Import dependencies first. Add a `RailVehicle3D` wrapper around an external
   model scene instance. Follow the existing clickable `VehicleCollider`, driving
   `Camera3D`, `VehicleDrivingParticles` and shared chimney-exhaust bridge.
   Wire the cylinder controller's `locomotive`, its particle nodes and the chimney
   controller's `locomotive`. Measure outlet positions and driving-wheel diameter.
5. Inspect the imported material in Godot. Check UVs, normal strength, texture
   dimensions and channels. Import success alone does not prove material parity:
   this importer drops the atlas's per-pixel specular response from
   `KHR_materials_specular`. The Harz wrapper uses one small ShaderMaterial to
   preserve G=roughness, B=metallic, A=Specular IOR Level, plus albedo and normals.
6. Add a unique key to `game/jsondata/rail_vehicle_types.json`. Set motor type,
   compatible gauge, measured model length, source-backed operating data, and the
   rounded price generated by `RailVehicleTypeData.PRICING.price_for()`.
   The existing factory, depot picker, audio and driving controls use this data;
   a new locomotive should not require changes to gameplay systems.
7. Run `sh tests/run-tests.sh harz_99_23_24 type_catalog rail_vehicle_pricing
   train_audio train_movement train_path rail_physics mpsb_12_exhaust`. The runner imports
   dependencies and refreshes script classes before testing. Read failing logs,
   distinguish new failures from baseline issues, and do not silently rebalance
   unrelated assets. Run the Godot scene-reference checker as well.
8. Confirm the wrapper opens in Godot and inspect the model at rail height on the
   correct gauge. Verify purchase/filtering, driving camera, forward movement,
   braking, reverse, steam and a compatible wagon. Coordinate with the user before
   interacting with a running session they are currently testing.
9. **The user creates `preview.png`.** Leave this file alone unless explicitly
   asked to make it. If asked, capture it in the Godot 3D editor with all gizmos
   hidden, environment enabled, and a well-framed three-quarter view, per AGENTS.

## Default reusable vehicle exporter (2026-11-25)

Use `tools/vehicles/export_vehicle.py` for **all future vehicle exports**. The
user explicitly requested this as the remembered default. It generalizes the
existing Harz exporter; extend this script for additional needs rather than
creating another vehicle-specific export implementation. The original Harz
script remains intact for historical rebuilds.

From the game project root:

```sh
/home/cornelinux/Apps/Blender5.2/blender -b --python-exit-code 1 \
  --python tools/vehicles/export_vehicle.py -- \
  --config tools/vehicles/configs/nwe_rollwagen_omm.json
```

Copy the config for the next asset and specify:

- `key`, game-relative `destination`, absolute `assembly_blend`, and total
  `material_count`.
- Each component's approved absolute `source`, exact source `object`, destination
  `name`, verified `triangles`, material `atlas_uv`, and optional assembly
  `offset_xyz` in Blender metres. One material per component is currently checked;
  extend the validation explicitly if a future approved mesh needs multiple slots.
- Two measured coupling attachment centres as `coupler_y_metres` and the measured
  wheel-tread plane as `tread_z_metres`. **Never infer a coupling centre from an
  asymmetric visual bounding box, rod tip, or wheel flange bottom.** Blender +Y
  exports as Godot -Z. A source pointing the other way must be oriented explicitly
  before using this configuration.

The script appends only named meshes, preserves source hashes, checks geometry,
UVs/normals, source triangle counts, packed textures and atlas UV-node references,
saves/reopens a packed editable assembly, and strips legacy UVs only in memory
for export. Export-only triangulation permits valid tangent generation on n-gons.
It writes separate `.gltf`, `.bin` and images, verifies referenced resources,
reimports the actual glTF, checks counts/UVs/bounds, and records results beside
`mesh/` in `import_report.json`. It does not merge approved components or modify
source files. This config intentionally preserves two meshes and two materials.
Godot wrapper/catalog registration, shader parity checks, gameplay tests and
visual inspection remain explicit integration steps; the exporter does not guess
operating specifications or alter gameplay.
